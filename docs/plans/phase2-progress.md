## Stage status

- **Stage 2.0, decisions and first measurements: in progress (started 17 October 2026).**
  - **Gate wording: agreed.** The owner agreed the proposed wording in `phase2.md`: ACC-2 on the raster development and check sets at 300 and 200 dpi greyscale, over all engravers, with pairs the owner agrees are faulty left out; ACC-4 on their exact pairs; 150 dpi, black and white and the real files reported, not gated.
  - **Real Type C files: none to be had.** The owner cannot get real clean raster files. MuseScore.com PDFs are made from the score and are Type A, so they do not help. The real-file check is the 21 commercial PDFs (Sibelius, Finale, Dorico) rendered as images, which come from engravers the project does not train on.
  - **Lyrics and chord symbols: in scope for raster input.** The owner chose to include them in Phase 2. REC-5 and REC-6 in `docs/requirements.md` now say "2 for raster input", and Stage 2.5 in `phase2.md` reads them.
  - **Raster sets.** `scripts/make_raster_set.py` renders every page of each pair into a PDF holding only the page image, in four versions (greyscale at 300, 200 and 150 dpi; black and white, 1 bit, at 300 dpi), each a set folder with its own `index.txt` under `generated/raster` on the corpus drive, named `<set>-g300`, `<set>-g200`, `<set>-g150` and `<set>-bw300`. The ground truth is the vector pair's file, and each pair's metadata gains the raster version, the source PDF and the page types. Every page written is inspected, and must be Type C. A stopped run can be started again; pairs already written are skipped. Score a version with `omr evaluate --set development --set-root <corpus>/generated/raster/development-g300 ...`.
    - Regression set: 256 pairs, 448 pages, all Type C in all four versions. About 5 minutes on 3 workers.
    - Commercial files: 21 files, 680 pages, all Type C in all four versions. They have no ground truth, so their folders hold `files.txt` instead of an index.
    - Development set (1,778 pairs, 10,927 pages) and check set (593 pairs, 3,335 pages): rendering.
  - **Inspector fault found and fixed.** The tilt search tried angles from minus 3 degrees upwards and kept the first best score, so a nearly blank last page (no ink in the middle band, every angle scoring zero) was measured as tilted by 3 degrees and called Type D. The search now tries angles nearest level first. Code: `raster_measures` in `src/omr/pdf/evidence.py`; spec in `docs/notes/inspector-spec.md`; 1 new test.
  - **`omr convert` and raster input.** An image file, or a PDF whose pages are images, is now named as such ("holds images of music, not vector music"), instead of "no staves were found". Reading them comes with Stage 2.4. 1 new test.
  - **Vector ceiling** (the vector reader's figures from Stage 1.8 run 3 and the Stage 1.9 check set run, the reference the raster path is measured against; results in `evaluations/s18-run3-*` and `evaluations/s18-check` on the corpus drive):
    - Development set, 1,778 pairs: notes 97.8 percent (LilyPond 94.9, MuseScore 3 98.8, MuseScore 4 98.8, Verovio 96.7); structure 80.4; ACC-6 93.1; ACC-4 88.3 percent with 4.3 percent of bars flagged.
    - Regression set, 256 pairs: notes 98.4 percent (LilyPond 93.7, MuseScore 3 99.6, MuseScore 4 99.2, Verovio 98.8); structure 80.5; ACC-6 99.4; ACC-4 94.1 percent with 5.4 percent of bars flagged.
    - Check set, 593 pairs (scored once, at Stage 1.9): notes 97.7 percent (LilyPond 93.5, MuseScore 3 99.0, MuseScore 4 98.5, Verovio 97.2); structure 83.1; ACC-6 93.1; ACC-4 75.0 percent with 3.1 percent of bars flagged.
    - Baseline sample, 355 pairs (the pairs Audiveris and homr were scored on, at 300 dpi): being scored from the Stage 1.8 run 3 outputs into `evaluations/s20-baseline-sample-omr`. At the Phase 1 gate it was 97.4 percent; Audiveris 86.3, homr 55.9.
  - **Starting weights.**
    - **Detector (Engine 1): YOLO11 nano from Ultralytics (AGPL-3.0).** No detector weights trained on DeepScores with a stated licence were found.
    - **Sequence reader (Engine 2): homr, chosen by the owner,** with SMT as the fallback. homr's code and weights are AGPL-3.0. It reads one staff at a time for any instrument. Its training data includes Camera-PrIMuS, whose Hugging Face copy is listed as non-commercial, which homr's own licence notes call an open question; it is listed under "Owner to resolve" in the licence register, to settle before a release. homr's size, counted from its files: encoder 13.2 million parameters, decoder 46.9 million (stored in INT8, which is why the Phase 0 estimate of 25 million was wrong), about 60 million in all. Staff image 256 by 1280 pixels; six token streams (rhythm, pitch, lift, articulation, slur, staff position), up to 608 tokens. PyTorch checkpoints are published (checkpoint 465 matches the current training code). SMT (`smt-grandstaff`): MIT, 21.4 million parameters, bekern tokens, trained on piano grand staves only.
    - **Does homr train in 2 GB: not yet measured.** `scripts/benchmark_homr_finetune.py` runs a few training steps on random data at batch 1 to 8, with and without the encoder frozen, and reports GPU memory and seconds a step. homr's source (commit ab369ac), checkpoint 465 and its training libraries are in `tools/dl/homr-src` on the corpus drive. Installing the last of those libraries and running homr's training code was stopped by the permission check, so the owner must allow it first.
  - **OCR engine: RapidOCR** (Apache-2.0, ONNX Runtime, PP-OCR models; installs on Python 3.14, where PaddlePaddle does not). Its default models read Chinese and English, so Stage 2.5 must measure PP-OCR's Latin model on lyrics; Tesseract is the fallback. In the licence register, not yet installed.
  - **Estimate** (agreed by the owner): 1 session; rendering 30 to 60 minutes on 3 CPU workers, no GPU; about 4 GB. **Actual:** the inspection of every page in all four versions takes about two thirds of the time, so the rendering takes about 3.5 to 4 hours on 3 workers (the owner agreed the longer run).
